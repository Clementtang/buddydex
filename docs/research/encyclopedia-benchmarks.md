## 3. BuddyDex 改進建議

### P0 — 核心體驗提升（應優先實作）

#### 3.1 搜尋與篩選系統

- **參考來源**：Scryfall 搜尋語法、Hearthstone 卡牌庫篩選面板、PokemonDB
- **預估工時**：M（中）
- **使用者價值**：高。18 隻目前還能一覽無遺，但若日後新增物種，搜尋是基本需求。即使現在，按稀有度/類型篩選也能提升探索樂趣
- **實作方向**：
  - 即時文字搜尋（名稱模糊匹配）
  - 篩選按鈕：稀有度（Common / Uncommon / Rare / Legendary）、是否有 Shiny 變體
  - 排序：依編號、稀有度、名稱字母序
  - 純前端實作，無需後端

#### 3.2 卡片稀有度視覺強化（全息 / 閃光效果）

- **參考來源**：Hearthstone Golden Card 動畫、CSS-Tricks 全息交易卡效果、Scryfall 閃卡標示
- **預估工時**：M（中）
- **使用者價值**：高。目前稀有度僅以文字呈現，加入 CSS 全息光效可大幅提升收藏感。純 CSS 即可實現
- **實作方向**：
  - Legendary 卡片邊框加入 `linear-gradient` + `background-blend-mode` 全息效果
  - Shiny 變體顯示時加入微光 shimmer 動畫
  - 使用 OKLCH 色彩空間製作漸層，視覺品質更佳
  - 尊重 `prefers-reduced-motion` 無障礙設定

#### 3.3 分享功能

- **參考來源**：PokemonDB Sprite 分享、WikiGacha 抽卡結果分享、Genshin 收藏分享
- **預估工時**：S（小）
- **使用者價值**：高。讓使用者能分享特定 Buddy 至社群，帶動自然流量
- **實作方向**：
  - 每個 Buddy 詳細頁提供「複製連結」按鈕（使用 URL hash 如 `#buddy-025`）
  - Web Share API（行動裝置原生分享選單）
  - 產生含 Buddy ASCII art 的分享圖片（Canvas API 或 html2canvas）

### P1 — 增強體驗（第二優先）

#### 3.4 個人收藏追蹤與完成度

- **參考來源**：YGOPRODeck 收藏追蹤、Genshin 完成度追蹤器、WikiGacha 里程碑
- **預估工時**：M（中）
- **使用者價值**：中高。讓使用者標記「已擁有」的 Buddy，顯示收集進度條。增加回訪動機
- **實作方向**：
  - localStorage 儲存收藏狀態（維持純靜態架構）
  - 進度條顯示 `已收集 / 18`
  - 收藏里程碑徽章（如：收集 5 隻、10 隻、全收集）
  - 卡片格狀視圖中以視覺方式區分已收集 vs 未收集

#### 3.5 音效系統

- **參考來源**：Pokedex 3D 叫聲音效
- **預估工時**：M（中）
- **使用者價值**：中。每隻 Buddy 有獨特音效增加辨識度與趣味性
- **實作方向**：
  - Web Audio API 合成簡單音效（避免載入音檔增加體積）
  - 開蛋時的破裂音效
  - 點擊 Buddy 時的反應音效
  - 預設靜音，使用者主動開啟

#### 3.6 詳細頁資訊架構強化

- **參考來源**：Bulbapedia 分區結構、PokemonDB 黏性目錄、FGO 技能效果表格
- **預估工時**：S（小）
- **使用者價值**：中。目前 Modal 資訊較扁平，可增加分頁或摺疊區塊
- **實作方向**：
  - 分頁顯示：基本資訊 / 配件試穿 / 圖鑑描述
  - 加入虛構的「生態描述」文字（類似 Pokedex 條目的風味文字）
  - 顯示該物種所有變體的縮圖一覽

### P2 — 錦上添花

#### 3.7 檢視模式切換

- **參考來源**：Hearthstone 卡片/表格雙模式
- **預估工時**：S（小）
- **使用者價值**：低中。部分使用者偏好緊湊的列表檢視
- **實作方向**：格狀 (Grid) / 列表 (List) 切換按鈕

#### 3.8 隨機探索功能

- **參考來源**：Scryfall Random Card 按鈕、Serebii Pokémon of the Week
- **預估工時**：S（小）
- **使用者價值**：低中。增加探索趣味
- **實作方向**：「隨機一隻」按鈕，直接開啟隨機 Buddy 的詳細頁

#### 3.9 語系名稱對照表

- **參考來源**：PokemonDB 8 語言名稱對照、Bulbapedia 語源學
- **預估工時**：S（小）
- **使用者價值**：低。已有 5 語系支援，可在詳細頁顯示該 Buddy 在各語言的名稱
- **實作方向**：詳細頁底部加入名稱對照表格

## 4. 跳脫框架的創意功能

### 4.1 Buddy 對戰系統

**概念**：使用者選擇自己的 Buddy，與其他 Buddy 進行簡單的回合制對戰。

**參考**：WikiGacha 的 ATK/DEF 對戰、Sylestia 回合制 RPG

**可行性分析**：

- 技術可行性：**高**。純前端可實作，數值基於稀有度和物種特性
- 工時：**L（大）**
- 趣味性：高，但需要平衡性設計
- 風險：可能偏離「百科全書」定位，變成遊戲。建議以「模擬對戰」定位，不涉及帳號系統
- **建議**：作為 Easter Egg 或實驗性功能，而非核心功能

### 4.2 社群排行榜 / 人氣投票

**概念**：使用者為喜歡的 Buddy 投票，顯示全站人氣排行。

**參考**：Serebii Pokémon of the Week、TierMaker 排名模板

**可行性分析**：

- 技術可行性：**中**。需要後端服務儲存投票（可用 Cloudflare Workers KV 或 Vercel KV）
- 工時：**M（中）**
- 使用者價值：中高，社群驅動型功能自帶傳播性
- 風險：需防刷票機制
- **建議**：可考慮。用 rate-limiting + fingerprint 防刷，輕量後端即可

### 4.3 HD / 3D 視覺化

**概念**：除了 ASCII art，提供高解析度 2D 插畫或 3D 模型檢視。

**參考**：Pokedex 3D 的 360 度旋轉、Genshin 角色模型檢視

**可行性分析**：

- 技術可行性：**低**。需要為每隻 Buddy 製作原創美術素材，這是內容問題而非技術問題
- 工時：**XL（極大）**，主要花在美術製作
- 使用者價值：高，但 ASCII art 正是 BuddyDex 的品牌特色
- **建議**：不建議。ASCII art 是差異化賣點，轉向 HD 會失去辨識度。若要嘗試，可考慮「像素風格」(pixel art) 作為折衷

### 4.4 抽卡 / 開包模擬器

**概念**：模擬抽卡體驗，隨機獲得 Buddy 卡片並加入收藏。

**參考**：YGOPRODeck Pack Simulator、WikiGacha 開包

**可行性分析**：

- 技術可行性：**高**。純前端即可，用機率表控制出貨率
- 工時：**M（中）**
- 使用者價值：高，抽卡機制天生有成癮性和分享動力
- 風險：需要搭配收藏追蹤系統才有意義
- **建議**：強烈推薦。可與現有 Hatch 動畫結合，做成「孵蛋抽卡」。每次隨機孵出一隻 Buddy，閃光有低機率觸發。搭配 localStorage 收藏系統

### 4.5 Buddy 圖鑑日記 / 發現紀錄

**概念**：記錄使用者首次發現每隻 Buddy 的時間和方式，類似 Pokedex 的發現/捕獲紀錄。

**可行性分析**：

- 技術可行性：**高**。localStorage 即可
- 工時：**S（小）**
- 使用者價值：中，增加個人化體驗
- **建議**：可作為收藏追蹤的附加功能，記錄發現時間戳

### 4.6 季節性 / 限定活動

**概念**：特定節日推出限定配件或色彩主題（如萬聖節、農曆新年）。

**可行性分析**：

- 技術可行性：**高**
- 工時：**S（每次活動）**
- 使用者價值：中高，製造回訪理由和社群討論
- **建議**：可考慮。低成本高回報，加入幾個節日限定帽子/眼睛即可

### 4.7 Buddy 性格 / 生態文字

**概念**：為每隻 Buddy 撰寫虛構的生態描述，類似 Pokedex 的風味文字。

**參考**：Bulbapedia Biology 段落、Pokecology 生態百科

**可行性分析**：

- 技術可行性：**高**
- 工時：**S（小）** — 文案撰寫為主
- 使用者價值：中高，豐富百科全書的「世界觀」
- **建議**：推薦。用 Claude 協助產生各語系的風味文字，強化 i18n 優勢

## 5. 不建議採用的功能

| 功能                    | 不建議原因                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| **使用者帳號系統**      | BuddyDex 是純靜態站，引入帳號系統會大幅增加複雜度（需後端、資料庫、認證）。localStorage 已足夠支撐收藏功能 |
| **HD / 3D 模型檢視**    | ASCII art 是品牌核心。製作 18 隻 HD 美術的成本極高，且會稀釋 terminal 美學的獨特性                         |
| **即時多人對戰**        | 需要 WebSocket 伺服器，維運成本高。BuddyDex 目前只有 18 隻，對戰深度不足以支撐即時多人                     |
| **社群論壇 / 留言系統** | 超出百科全書範疇，需要內容審核機制。可用外部社群（Discord / Reddit）替代                                   |
| **牌組 / 隊伍編輯器**   | YGOPRODeck 和 Scryfall 的牌組功能建立在龐大卡池之上。18 隻的池子太小，隊伍編輯意義不大                     |
| **價格追蹤**            | Buddy 不是實體交易商品，沒有次級市場，此功能無適用場景                                                     |
| **Wiki 式社群編輯**     | Bulbapedia 模式需要大量貢獻者和管理員。BuddyDex 是單一維護者專案，不適合開放編輯                           |
| **完整 API**            | 目前資料量太小（18 筆），提供 API 的投入產出比不合理。待物種數量成長後再評估                               |
